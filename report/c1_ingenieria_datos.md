# C1 — Ingeniería de datos y representación de secuencias

El perfilado de PaySim encontró 6,353,307 remitentes para 6,362,620 transacciones: 99.85% aparece una sola vez y ninguno alcanza cinco operaciones. Esto deja poco historial para aprender frecuencia y comportamiento temporal por remitente. En contraste, IBM AML HI-Small contiene 5,078,345 transacciones de 496,999 cuentas emisoras, de las cuales 128,779 tienen cinco operaciones o más. Por ello se conserva PaySim como evidencia exploratoria y se utiliza HI-Small para las secuencias. Las etiquetas no se mezclan: PaySim representa fraude e IBM representa lavado. IBM AML es sintético y modela bancos, individuos y empresas; por tanto, los resultados no describen directamente las remesas guatemaltecas reales (Altman et al., 2023).

Para mantener el proceso dentro del presupuesto de Google Colab, se seleccionaron uniformemente 50,000 cuentas emisoras, sin consultar su etiqueta, con una semilla fija de 42. Cada remitente se identifica mediante el par banco–cuenta y sus operaciones se ordenan por fecha; la posición original de la fila resuelve empates. Se conservan las 64 transacciones más recientes. Esta longitud cubre el 97.39% de los historiales seleccionados sin recorte: de 464,009 operaciones se retienen 426,244. Después del recorte se recalcula la etiqueta de cada secuencia utilizando solamente operaciones visibles para el modelo. Los remitentes positivos bajan de 366 a 362 y las operaciones positivas de 533 a 525. Así se evita etiquetar una secuencia como sospechosa por evidencia que fue descartada.

Cada transacción se representa mediante importe pagado con transformación logarítmica, tiempo desde la operación anterior, operaciones anteriores en 24 horas, hora y día de semana en forma cíclica, transferencia entre bancos, repetición previa del destinatario, moneda y formato de pago. Las variables históricas se calculan causalmente: una operación futura no cambia features anteriores. Los importes de monedas distintas no se convierten; la moneda permanece como variable categórica. Identificadores, nombres y etiquetas se guardan para trazabilidad y nunca ingresan al tensor.

La media y desviación de las tres variables logarítmicas se ajustan solo con transacciones de secuencias normales de entrenamiento, tal como requiere la etapa A. Los vocabularios categóricos se ajustan con el conjunto de entrenamiento y reservan una categoría desconocida para validación, prueba e inferencia. El resultado tiene 33 features. No se utiliza SMOTE ni sobremuestreo, por lo que se conserva la prevalencia observada. En entrenamiento quedaron 34,746 secuencias normales y 254 positivas; el cociente negativo/positivo es 136.80 y se entrega como posible `pos_weight` para que la etapa B decida cómo incorporarlo a su pérdida.

Los splits contienen 35,000 remitentes de entrenamiento, 7,500 de validación y 7,500 de prueba, con 254, 54 y 54 positivos. El catálogo Accounts mostró que una entidad puede poseer varias cuentas. Por esa razón, la separación se realizó agrupando por `Entity ID`: ninguna entidad seleccionada aparece en más de un conjunto, aunque las secuencias siguen siendo por cuenta. Esta decisión evita que el modelo vea otra cuenta del mismo actor durante entrenamiento. La partición mide generalización a entidades no vistas, pero no es prospectiva en el tiempo y puede compartir destinatarios o bancos entre conjuntos.

El pipeline persiste arrays concatenados y offsets en NPZ, filas originales en Parquet y manifiestos JSON con configuración, orden de features, hashes de los CSV, conteos y tiempos. Los modelos reciben la misma máscara de padding y exactamente los mismos splits. El MVP puede recuperar las filas originales en el orden del tensor para explicar qué operaciones activaron una alerta. La generación local completa tomó 49.7 segundos; el notebook debe verificarse todavía en una GPU T4 junto con el entrenamiento completo para demostrar el límite global de treinta minutos.

**Referencia:** Altman, E., Blanuša, J., von Niederhäusern, L., Egressy, B., Anghel, A., & Atasu, K. (2023). *Realistic Synthetic Financial Transactions for Anti-Money Laundering Models*. NeurIPS Datasets and Benchmarks.
